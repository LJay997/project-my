## 二、库存层：超卖根治与阿里内部方案（题 1、2、3、9）

**题1 · 超卖 Bug 实战重现**
根因就是上图左：**"读库存→判断→扣减"三步非原子**。压测下两个线程同时读到 `stock=1`，各自判断通过、各自扣减，库存打成 -1。高并发下这种竞态会被放大成几十万级超卖。

**题2 · 阿里内部高并发秒杀下单方案**
核心是**"分层过滤 + 预扣减 + 异步落库"**：
- **分层过滤**：CDN/网关逐层丢弃无效请求，让真正打到 Redis 的流量只有原始的 1‰。
- **Redis 预扣减**：库存提前预热到 Redis，用 **Lua 脚本原子扣减**（上图右），扣减成功立即返回用户"排队中"。
- **异步落库**：扣减成功后写 MQ，订单服务消费后写 DB，DB 压力被 MQ 削到可承受水位。
- 关键点：**Redis 是库存的"真相源"，DB 只是最终账本**（活动期间以 Redis 为准，结束后对账）。

**题3 · Redis + MQ 下单架构**
即第 ③→④ 层：`Redis 原子扣减 → 成功则发 MQ → 订单服务消费落库`。Redis 承担**瞬时高并发扣减**（10w+ QPS），MQ 承担**削峰填谷 + 异步解耦**，DB 按消费速率平稳写入。

**题9 · 主从切换导致库存同步异常 / 超卖**
- 痛点：Redis 主从异步复制，**主刚扣减、未同步到从就宕机**，切换后从库是旧库存 → 库存"回滚" → 超卖。
- 解法：
    - **库存热点 key 不走从库**：扣减只读主，查询降级走从或缓存。
    - **同步复制 + redlock 强一致**：对库存 key 用 `WAIT` 指令或 Redisson 同步锁保证多数节点落盘（牺牲少量性能换一致）。
    - **库存分段**：把 `sku:100` 拆成 `sku:100:0..9` 十个桶，降低单 key 热点，主从切换时单桶影响面小、易对账修复。

## 三、MQ 削峰层：不丢、幂等、积压、高可用（题 5、6、7、10）

**题5 · 不丢消息**
上图三段缺一不可：① 生产端用 **confirm/ack** + **本地消息表**（写库后异步投递、失败重试补发）；② Broker **消息落盘 + 多副本同步**；③ 消费端**手动 ack**——业务成功后才 ack，处理中宕机消息会重投。

**题6 · 重复消费幂等**
网络重投必然发生，幂等三件套：
- **业务唯一键**：`订单号` 或 `userId+skuId+活动ID` 组合。
- **去重表**：消费前 `INSERT` 去重表（唯一索引冲突即重复），或 Redis `SETNX` 标记。
- **状态机**：订单 `未支付→已支付` 只能单向流转，重复消费读到终态直接跳过。
  关键：**幂等判断与业务写入必须在同一事务/同一原子操作内**，否则仍可能漏。

**题7 · 百万订单积压**
- **临时扩容消费者** + **Topic 分区扩容**（注意分区数与消费者数匹配，避免空转）。
- **降级消费**：积压严重时只写核心字段（订单号、用户、库存），非核心字段异步补全。
- **跳过堆积**：极端场景直接消费最新消息跳过历史（牺牲一致性换可用），事后对账修复。

**题10 · MQ 集群崩溃高可用**
- **多机房多活部署** + **主从自动切换**（Kafka Controller / RocketMQ DLedger Raft）。
- **降级预案**：MQ 不可用时，秒杀请求落到**本地消息表 + 限流降级**，集群恢复后批量补发；或**直接拒绝下单**（保护 DB 不被直击）。
- **熔断**：消费端异常率超阈值自动熔断，防雪崩。

## 四、性能与高可用（题 4、8、11）

**题4 · 10w 订单/秒热点数据架构优化**
- **热点拆分**：把单热点 key（爆款 sku）拆成 `sku:1000:0..99` 100 个分桶，扣减时随机/轮询选桶，单 key QPS 从 10w 降到 1000，破除单点瓶颈。
- **本地缓存**：库存状态用 Caffeine 多级缓存（本地 + Redis），读请求尽量不穿透 Redis。
- **连接池/管道**：Redis 用 Pipeline 批量、连接池复用；MQ 批量发送。
- **读多写少分离**：查询走从库/缓存，扣减只打主库。

**题8 · Redis 集群崩溃高可用**
- **哨兵/Cluster 自动故障转移**：主宕机秒级提升从为主。
- **多副本**：至少 1 主 2 从，保证单节点宕机不丢数据。
- **降级**：Redis 全挂时，库存**降级到本地缓存 + 限流到 DB 可承受水位**，或直接暂停活动（防超卖优先于保可用）。
- **预热恢复**：集群恢复后从 DB/快照重新预热库存。

**题11 · Redis 与 MQ 事务一致性**
这是最难的一题，核心是**分布式事务最终一致**，主流方案二选一：
- **本地消息表（可靠消息）**：扣减库存 + 写本地消息表在同一**本地事务**内（强一致）；后台定时扫表投递 MQ；消费端幂等处理。保证"扣减成功则必有下单消息"。
- **事务消息（RocketMQ TXMsg）**：先发 half 消息 → 执行本地扣减 → commit/rollback half 消息；Broker 回查本地事务状态。保证"本地事务与消息发送原子绑定"。
- 失败补偿：消费端处理失败 → 死信 → 人工/自动对账 → **回滚库存**（补偿事务，最终一致）。
- 关键原则：**Redis 扣减是预扣，DB 才是真实库存账本**；任何环节失败都要能通过"消息+对账"恢复到一致状态。
