## 1. 跨域请求概述

### 1.1 定义与产生原因

#### 什么是跨域？

当一个资源从**协议、域名或端口**中任一不同的另一资源请求数据时，浏览器执行的**安全限制**就是跨域。

```
┌─────────────────────────────────────────────────────────────────────┐
│                        跨域场景示意图                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  前端页面: http://www.example.com:8080/index.html                   │
│  请求目标: http://api.example.com:9090/users                        │
│                                                                     │
│  对比项:                                                             │
│  ┌──────────┬──────────────┬──────────────┬──────────┐              │
│  │   协议    │   域名        │   端口        │  是否跨域  │              │
│  ├──────────┼──────────────┼──────────────┼──────────┤              │
│  │   http   │  www.example │    8080       │  -        │              │
│  │   http   │  api.example │    9090       │  ✅ 跨域   │              │
│  └──────────┴──────────────┴──────────────┴──────────┘              │
│                                                                     │
│  触发条件（满足任一即跨域）:                                           │
│  ① 协议不同: http:// → https://                                     │
│  ② 域名不同: www.example.com → api.example.com                      │
│  ③ 端口不同: 8080 → 9090                                           │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

#### 跨域的本质

跨域是**浏览器的安全机制**，而非服务器的限制。服务器之间的请求不存在跨域问题。

### 1.2 同源策略详解

#### 同源的判断标准

两个 URL **同源**当且仅当它们有相同的：

1. **协议**（Protocol）- `http` 或 `https`
2. **主机名**（Host）- `example.com`
3. **端口号**（Port）- `80` 或 `443`

```
示例：
http://example.com:8080/path1  ←→  http://example.com:8080/path2  ✅ 同源
http://example.com:8080/path  ←→  https://example.com:8080/path  ❌ 不同协议
http://example.com:8080/path  ←→  http://api.example.com:8080/path  ❌ 不同域名
http://example.com:8080/path  ←→  http://example.com:9090/path  ❌ 不同端口
```

#### 同源策略的限制范围

| 受限操作 | 说明 |
|----------|------|
| **Ajax 请求** | XMLHttpRequest/fetch 受限制 |
| **DOM 操作** | 无法操作不同源页面的 DOM |
| **Cookie 读取** | 无法读取不同源的 Cookie |
| **localStorage** | 不同源无法共享 |
| **IndexedDB** | 按源隔离 |

#### 不受同源策略限制的操作

| 操作 | 说明 |
|------|------|
| `<script src="...">` | 可以跨域加载 JS 文件 |
| `<img src="...">` | 可以跨域加载图片 |
| `<link href="...">` | 可以跨域加载 CSS |
| `<iframe src="...">` | 可以跨域嵌入页面 |
| `window.open()` | 可以打开跨域窗口 |

## 2. 跨域解决方案

### 2.1 方案对比总览

| 方案 | 原理 | 优点 | 缺点 | 适用场景 |
|------|------|------|------|----------|
| **JSONP** | `<script>` 标签加载 | 实现简单 | 只支持 GET | 老项目兼容 |
| **CORS** | HTTP 响应头协商 | 标准方案 | 预检请求开销 | **推荐方案** |
| **代理服务器** | 同源代理转发 | 无需修改 | 增加延迟 | 开发环境 |
| **iframe** | iframe + postMessage | 实时通信 | 实现复杂 | 嵌入式应用 |
| **WebSocket** | 全双工通信 | 不受限制 | 保持连接 | 实时通信 |
| **nginx 代理** | nginx 反向代理 | 零代码 | 运维配置 | **生产首选** |

### 2.2 JSONP

#### 实现原理

利用 `<script>` 标签不受同源策略限制的特性，动态创建 script 标签，请求后端接口，后端返回 JS 代码包裹的数据。

#### 前端实现

```javascript
// 原生实现
function jsonp(url, callback) {
    const callbackName = 'jsonp_callback_' + Date.now();
    window[callbackName] = callback;
    
    const script = document.createElement('script');
    script.src = url + '?callback=' + callbackName;
    script.onerror = function() {
        delete window[callbackName];
        script.remove();
        callback(new Error('请求失败'));
    };
    document.body.appendChild(script);
}

// 使用
jsonp('http://api.example.com/user', function(data) {
    console.log('用户数据:', data);
});
```

#### 后端实现（Spring Boot）

```java
@RestController
public class JsonpController {

    @GetMapping(value = "/api/user", produces = "application/javascript")
    public String getUser(
            @RequestParam(value = "callback", required = false) String callback) {
        
        Map<String, Object> data = Map.of("id", 1, "name", "张三");
        String json = JSON.toJSONString(data);
        
        if (callback == null || callback.isEmpty()) {
            return json;
        }
        return callback + "(" + json + ")";
    }
}
```

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 实现简单，兼容性好 | 只支持 GET 请求 |
| 不受同源策略限制 | 存在 XSS 安全风险 |
| 无需后端复杂配置 | 无法发送自定义 Header |

### 2.3 CORS（推荐方案）

#### 工作流程

```
简单请求:
  浏览器 → GET/POST → 服务器
  服务器返回 Access-Control-Allow-Origin 等头部

预检请求（非简单请求）:
  浏览器 → OPTIONS(预检) → 服务器
  服务器返回允许的源/方法/头部
  浏览器 → 实际请求 → 服务器
```

#### Spring Boot 实现

##### 方式一：@CrossOrigin 注解

```java
@RestController
@RequestMapping("/api")
public class UserController {

    @CrossOrigin(
        origins = "http://localhost:3000",
        methods = {RequestMethod.GET, RequestMethod.POST},
        allowedHeaders = {"Content-Type", "Authorization"},
        allowCredentials = "true",
        maxAge = 3600
    )
    @GetMapping("/users")
    public List<User> getUsers() {
        return userService.findAll();
    }
}
```

##### 方式二：全局配置（推荐）

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/api/**")
            .allowedOrigins("http://localhost:3000", "https://example.com")
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("Content-Type", "Authorization", "X-Requested-With")
            .exposedHeaders("X-Total-Count", "X-Custom-Header")
            .allowCredentials(true)
            .maxAge(3600);
    }
}
```

##### 方式三：CorsFilter Bean

```java
@Configuration
public class CorsFilterConfig {

    @Bean
    public CorsFilter corsFilter() {
        CorsConfiguration config = new CorsConfiguration();
        config.addAllowedOrigin("http://localhost:3000");
        config.addAllowedMethod("*");
        config.addAllowedHeader("*");
        config.setAllowCredentials(true);
        config.setMaxAge(3600L);
        
        UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
        source.registerCorsConfiguration("/**", config);
        return new CorsFilter(source);
    }
}
```

#### CORS 关键响应头

| 响应头 | 作用 |
|--------|------|
| `Access-Control-Allow-Origin` | 允许的源（必填） |
| `Access-Control-Allow-Methods` | 允许的 HTTP 方法 |
| `Access-Control-Allow-Headers` | 允许的请求头 |
| `Access-Control-Allow-Credentials` | 是否允许携带 Cookie |
| `Access-Control-Max-Age` | 预检请求缓存时间 |
| `Access-Control-Expose-Headers` | 暴露给 JS 的响应头 |

### 2.5 iframe + postMessage

#### 实现原理

利用 iframe 嵌入跨域页面，通过 `postMessage` API 实现父子窗口通信。

```javascript
// 父页面
const iframe = document.getElementById('child-frame');

// 发送消息
iframe.contentWindow.postMessage(
    { type: 'GET_USER', id: 1 },
    'http://child.com'  // 目标源
);

// 接收消息
window.addEventListener('message', (e) => {
    if (e.origin !== 'http://child.com') return;  // 安全检查
    console.log('收到:', e.data);
});

// 子页面
window.addEventListener('message', (e) => {
    if (e.origin !== 'http://parent.com') return;  // 安全检查
    // 处理并响应
    e.source.postMessage({ type: 'RESPONSE', data: result }, e.origin);
});
```

## 3. 前后端实现代码示例

### 3.1 Spring Boot 完整实现

#### 配置文件

```yaml
# application.yml
app:
  cors:
    enabled: true
    allowed-origins:
      - http://localhost:3000
      - https://example.com
    allowed-methods: GET,POST,PUT,DELETE,OPTIONS
    allowed-headers: Content-Type,Authorization,X-Requested-With
    max-age: 3600
    allow-credentials: true
```

#### CORS 配置类

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Value("${app.cors.allowed-origins}")
    private String[] allowedOrigins;

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
            .allowedOriginPatterns(allowedOrigins)
            .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
            .allowedHeaders("*")
            .exposedHeaders("X-Total-Count", "X-Request-Id")
            .allowCredentials(true)
            .maxAge(3600);
    }
}
```

#### 带 Token 的认证示例

```java
@RestController
@RequestMapping("/api/auth")
public class AuthController {

    @PostMapping("/login")
    public ResponseEntity<?> login(@RequestBody LoginRequest request) {
        User user = userService.validate(request);
        String token = jwtTokenProvider.generateToken(user);
        
        return ResponseEntity.ok()
            .header("Authorization", "Bearer " + token)
            .header("Access-Control-Expose-Headers", "Authorization")
            .body(Map.of("userId", user.getId(), "token", token));
    }
}
```

### 3.2 Vue + Axios 前端实现

```javascript
// src/utils/api.js
import axios from 'axios';

const api = axios.create({
    baseURL: '/api',
    timeout: 10000
});

// 请求拦截器
api.interceptors.request.use(config => {
    const token = localStorage.getItem('token');
    if (token) {
        config.headers['Authorization'] = `Bearer ${token}`;
    }
    return config;
});

// 响应拦截器
api.interceptors.response.use(
    response => response.data,
    error => {
        if (error.response?.status === 401) {
            localStorage.removeItem('token');
            window.location.href = '/login';
        }
        return Promise.reject(error);
    }
);

export default api;
```

## 4. 安全问题与防范

### 4.1 常见安全风险

| 风险类型 | 描述 | 危害等级 |
|----------|------|----------|
| `*` + credentials | 通配符源 + 凭证同时使用 | 🔴 高 |
| Origin 验证不严格 | 正则匹配过于宽松 | 🔴 高 |
| JSONP 回调注入 | 未过滤 callback 参数 | 🔴 高 |
| postMessage 未验证 origin | 不检查消息来源 | 🔴 高 |
| CSRF 攻击 | 利用已登录身份发起请求 | 🔴 高 |

### 4.2 防范措施

#### 安全的 CORS 配置

```java
// ❌ 不安全
@CrossOrigin(origins = "*", allowCredentials = "true")

// ✅ 安全
@CrossOrigin(origins = {"https://admin.example.com"})

// 生产环境白名单
private static final Set<String> ALLOWED_ORIGINS = Set.of(
    "https://admin.example.com",
    "https://user.example.com"
);
```

#### JSONP 安全验证

```java
@GetMapping("/api/data")
public String getData(
        @RequestParam(value = "callback", required = false) String callback) {
    
    String json = JSON.toJSONString(getDataService());
    
    // 验证 callback 格式
    if (callback != null && !callback.isEmpty()) {
        if (!callback.matches("^[a-zA-Z_][a-zA-Z0-9_.]*$")) {
            throw new IllegalArgumentException("非法的回调函数名");
        }
        if (callback.length() > 50) {
            throw new IllegalArgumentException("回调函数名过长");
        }
        return callback + "(" + json + ")";
    }
    return json;
}
```

#### postMessage 安全使用

```javascript
// 接收消息时验证 origin
const ALLOWED_ORIGINS = ['https://trusted-source.com'];

window.addEventListener('message', (e) => {
    if (!ALLOWED_ORIGINS.includes(e.origin)) {
        console.warn('不受信任的来源:', e.origin);
        return;
    }
    if (typeof e.data !== 'object' || !e.data.type) {
        return;
    }
    // 处理消息...
});
```

#### 安全响应头

```java
@Component
public class SecurityHeadersInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request,
                              HttpServletResponse response, Object handler) {
        response.setHeader("X-Content-Type-Options", "nosniff");
        response.setHeader("X-Frame-Options", "DENY");
        response.setHeader("X-XSS-Protection", "1; mode=block");
        response.setHeader("Referrer-Policy", "strict-origin-when-cross-origin");
        return true;
    }
}
```

## 5. 排查与调试方法

### 5.1 浏览器开发者工具

#### Chrome DevTools 调试步骤

```
1. 打开 DevTools (F12)
2. 切换到 Network 标签
3. 触发跨域请求
4. 查看请求详情:
   - Request Headers: Origin、Access-Control-Request-Method
   - Response Headers: Access-Control-Allow-Origin 等
   - Status Code: 200(成功) / 403(被拒绝)
5. 查看 Console 标签的错误信息
```

#### 常见错误与排查

| 错误信息 | 可能原因 | 排查方法 |
|----------|----------|----------|
| `No 'Access-Control-Allow-Origin'` | 后端未配置 CORS | 检查响应头 |
| `preflight request doesn't pass` | 预检请求被拒绝 | 检查 OPTIONS 请求 |
| `credential mode is 'include'` | credentials 配置不一致 | 检查前后端配置 |
| `blocked by CORS policy` | Origin 不在白名单 | 检查 Origin 和白名单 |

#### 使用 curl 测试

```bash
# 测试 CORS 头
curl -v -H "Origin: http://localhost:3000" http://api.example.com/users

# 模拟预检请求
curl -v -X OPTIONS \
  -H "Origin: http://localhost:3000" \
  -H "Access-Control-Request-Method: POST" \
  -H "Access-Control-Request-Headers: Content-Type" \
  http://api.example.com/users
```

### 5.3 常见问题定位

#### 问题1：预检请求被拒绝

```
现象: 浏览器报 "preflight request doesn't pass"
排查: 检查 OPTIONS 请求响应是否包含 CORS 头
解决: 确保后端正确处理 OPTIONS，配置正确的 allowedHeaders
```

#### 问题2：自定义 Header 被拒绝

```
现象: 添加 Authorization Header 后请求失败
原因: 自定义 Header 触发预检请求
解决: 配置允许的 Header 列表
```

#### 问题3：Cookie 无法携带

```
现象: 请求未携带 Cookie
排查: 
  1. 前端检查 withCredentials: true
  2. 后端检查 Allow-Credentials: true
  3. Allow-Origin 不能为 "*"
```

#### 问题4：响应头无法获取

```
现象: 前端无法读取自定义响应头
原因: 自定义响应头默认不可访问
解决: 配置 exposedHeaders
```

#### 问题5：多个 CORS 配置冲突

```
现象: 响应包含重复 CORS 头
原因: nginx + Spring 同时配置
解决: 统一在一处配置，移除重复配置
```

## 6. 高频面试题解析

### Q1: 什么是跨域？为什么会有跨域问题？

**答案**：跨域是浏览器中不同源之间的资源访问限制。原因是浏览器的同源策略保护机制，防止恶意网站窃取用户数据、发起 CSRF 攻击。

**追问点**：
- 什么是同源？
- 哪些操作受跨域限制？
- 哪些操作不受限制？

---

### Q2: CORS 预检请求是什么？什么时候会触发？

**答案**：预检请求是浏览器在发送非简单请求前自动发送的 OPTIONS 请求，用于询问服务器是否支持跨域。

**触发条件**：
1. 使用 PUT/DELETE/PATCH 等方法
2. Content-Type 不是默认类型
3. 包含自定义 Header（如 Authorization）

---

### Q3: 各种跨域方案的优缺点和适用场景？

**答案**：

| 方案 | 适用场景 |
|------|----------|
| **CORS** | 前后端分离（推荐） |
| **JSONP** | 老系统兼容、只需要 GET |
| **代理服务器** | 开发环境调试 |
| **nginx 代理** | 生产环境首选 |
| **postMessage** | iframe 父子通信 |
| **WebSocket** | 实时通信场景 |

---

### Q4: CORS 中 `Access-Control-Allow-Origin` 可以设置为 `*` 吗？

**答案**：
- 可以，但**不能**与 `Access-Control-Allow-Credentials: true` 同时使用
- 生产环境应使用具体的域名白名单
- 安全原因：`*` 会导致任何网站都可以发起带凭证的请求

---

### Q5: 如何解决跨域携带 Cookie 的问题？

**答案**：
1. **后端**：配置 `Access-Control-Allow-Credentials: true`，`Allow-Origin` 不能为 `*`
2. **前端**：设置 `withCredentials: true`（axios）或 `credentials: 'include'`（fetch）
3. **Cookie**：设置 `SameSite` 属性为 `None` 允许跨站携带

---

### Q6: CORS 和 JSONP 有什么区别？

**答案**：

| 对比项 | CORS | JSONP |
|--------|------|-------|
| 请求方式 | 所有 HTTP 方法 | 仅 GET |
| 数据类型 | 任意 | 仅 JSON |
| 安全性 | 安全（服务器验证） | 不安全（回调注入） |
| 实现复杂度 | 中等 | 简单 |
| 标准性 | W3C 标准 | 非标准 |

---

### Q7: 如何防止 CORS 攻击？

**答案**：
1. **严格白名单**：`Allow-Origin` 使用具体域名，不要用 `*`
2. **验证 Origin**：服务器端验证请求的 Origin 头
3. **CSRF Token**：关键操作添加 CSRF Token
4. **JSONP 验证**：验证 callback 参数格式
5. **postMessage 验证**：接收消息时检查 origin
6. **安全响应头**：配置 X-Frame-Options、CSP 等

---

### Q8: 开发环境和生产环境如何处理跨域？

**答案**：
- **开发环境**：使用 devServer proxy（Vue/Vite）转发请求，前端无感知
- **生产环境**：使用 nginx 反向代理统一入口，或后端配置 CORS
- **微服务架构**：使用 API Gateway（Spring Cloud Gateway）统一处理

---

### Q9: 预检请求会影响性能吗？如何优化？

**答案**：预检请求会增加一次 HTTP 往返，有一定影响。优化方法：
1. 设置 `Access-Control-Max-Age` 缓存预检结果（如 3600 秒）
2. 尽量使用简单请求（避免自定义 Header）
3. 使用 nginx 直接处理 OPTIONS 请求
4. 服务端缓存常用的 CORS 配置

---

### Q10: 说一下你在项目中是如何处理跨域的？

**参考回答**：
1. **开发环境**：使用 Vite devServer proxy，将 `/api` 前缀的请求代理到后端 8080 端口
2. **生产环境**：
   - 方案一：nginx 反向代理，前端和 API 同域部署
   - 方案二：Spring Boot CORS 配置，通过 `CorsRegistry` 设置白名单
3. **安全措施**：
   - Origin 白名单验证
   - 禁止 `*` + `credentials` 组合
   - JSONP 回调函数格式验证
   - 关键接口添加 CSRF Token

### 跨域问题排查 Checklist

```
□ 确认问题类型

  □ Origin 头是否正确？
  □ 是否有 Access-Control-Request-Method？

  □ 是否有 Access-Control-Allow-Methods？
  □ 是否有 Access-Control-Allow-Headers？
  □ 是否有 Access-Control-Allow-Credentials？

□ 验证配置
  □ 后端 CORS 配置是否正确？
  □ nginx 代理是否正确转发？
  □ 前端 baseURL 是否正确？

□ 安全检查
  □ Allow-Origin 是否为具体域名？
```
