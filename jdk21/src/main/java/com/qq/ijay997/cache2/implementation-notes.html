设计决策关键决策记录

决策点结论与依据
Redis 键前缀写法 prefixCacheNameWith(globalPrefix + ":")。javap 字节码验证：CacheKeyPrefix.prefixed(p) 的 lambda 为 p + cacheName + ":"，会自动追加缓存名与分隔符；且 RedisCache.prefixCacheKey = getKeyPrefixFor(this.name) + key。最终键：kjgl-rp:{cacheName}:t{tenantId}:{bizKey}。前缀含缓存名段是 @CacheEvict(allEntries=true) 前缀 SCAN 不跨缓存误删的前提。
Caffeine 实例按 baseName 归一化 TtlCaffeineCacheManager 自维护 cachesByBaseName，剥离 #ttl 后按基础名建/取实例。原因：本地缓存没有 Redis 的共享物理键空间，若按完整名（含 #ttl）建实例，@Cacheable("caffeine:a#120") 与 @CacheEvict("caffeine:a") 会落在两个 Caffeine 实例上，evict 落空。
Redis 通道保留父类完整名 cacheMap lov-cache#600 与 lov-cache 是两个 RedisCache 实例，但键前缀相同、共享同一物理键空间，跨 TTL 变体 evict 天然一致，无需归一化。
TTL 解析职责放在 CacheManager，通道分流放在 CacheResolver RoutingCacheResolver 仅做前缀路由并把 #ttl 段原样下传；两个官方管理器子类各自解析（规则一致：内嵌 #秒数 > yml cache.ttl.* 分桶 > cache.default-ttl-seconds）。单一职责，替换任一层不动其余。
租户隔离置于 TenantCacheResolver（装饰层） SpEL key 与 keyGenerator 在 Spring CacheOperation 构建期互斥，租户段不能进 KeyGenerator/SpEL；装饰 Cache 统一拼 t{tenantId}:，SpEL 仅算业务键，注解零定制。
不覆写 CachingConfigurer.cacheManager() 已提供全局 cacheResolver()，缓存拦截器不再回退查询 CacheManager Bean，两个通道 Bean 无歧义；@Primary 加在 redisCacheManager 上仅作容器内其他组件按类型注入的兜底。
新通道扩展方式 RoutingCacheResolver.registerChannel(前缀, CacheManager)，路由表为 LinkedHashMap（初始化期注册，非线程安全），新增通道零改解析逻辑。

偏差相对已批准计划的偏离

计划草案实际实现原因
prefixCacheNameWith(globalPrefix + ":" + baseName + ":")（计划与原 TenantRoutingCacheManager 均如此） prefixCacheNameWith(globalPrefix + ":") 字节码证明草案写法会叠加自动追加的 cacheName，产生 kjgl-rp:lov-cache:lov-cache:t1:… 重复键段。原方案 A 类的该隐患随本类删除一并消除（尚未运行部署，无迁移成本）。
TtlCaffeineCacheManager：无 # 走 super.getCache，含 # 走自维护 dynamicCaches（按完整名） 统一覆写 getCache，全部按 baseName 归一化 + 自维护 cachesByBaseName；getCacheNames() 一并覆写 草案两条路径产出不同 Caffeine 实例，跨 TTL 变体 evict 落空（详见设计决策表）。归一化是正确性前提。
计划摘要表述"剥离 #ttl 段 → getCache(基础名)" 保留 #ttl 段整名传给目标 CacheManager 以计划详细设计（"剥通道前缀，保留 #ttl"）为准；若提前剥离，内嵌 TTL 信息丢失、语法失效。

权衡备选方案与取舍

权衡点选择放弃的备选与理由
Caffeine 同基础名多 TTL 变体 first-arrival：TTL 取首个到达请求解析的值 每变体独立实例会破坏 evict；Caffeine 变长过期（Expiry API）需按 key 反查 TTL、复杂度高且与官方 CaffeineCache 适配割裂。同基础名不同 TTL 的正确姿势是 yml 分桶统一声明。
extends 官方管理器 vs 自实现 CacheManager extends RedisCacheManager / CaffeineCacheManager 自实现需重造键计算、SCAN 清理、事务语义、allowNullValues 适配等；extends 仅覆写创建钩子，官方语义全部保留（也符合用户"使用官方 CacheManager 组合"的诉求）。
父类 cacheMap vs 自维护实例池 Redis 用父类 cacheMap（完整名 key）；Caffeine 用自维护 map（baseName key） Redis 键空间共享、父类机制够用；Caffeine 需要归一化语义，父类 cacheMap 无法表达。
两个 CacheManager Bean vs 继续单 Bean 两个标准 Bean + @Primary（Redis） 方案 A 单类虽无 Bean 歧义，但扩展需改类；Boot CacheAutoConfiguration 对多 Bean 场景正常退避，actuator 按 Map<String, CacheManager> 注入兼容多 Bean。
