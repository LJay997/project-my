实现说明：远端接口调用本地消息表（Transactional Outbox）

针对「文件导入、数据新建、编辑、删除」四类业务场景接入远端接口调用，采用事务发件箱（Transactional Outbox）+ 本地消息表方案，实现异步解耦、批量发送、失败重试与状态全链路追踪。

一、设计决策（Design Decisions）

#决策点选择与理由
1事务监听机制使用 Spring 原生 @TransactionalEventListener(phase = AFTER_COMMIT)（即项目笔记中的「事务监听机制」），配合 @Async 在专用线程池异步执行。
2本地消息表新建 JPA 实体 RemoteMessage（表 t_remote_message），持久化远端请求参数（序列化为 JSON 字符串）。
3状态模型四态：PENDING / SENDING / SUCCESS / FAILED，配合 RemoteMessageLog 记录每次状态变更，形成全链路轨迹。
4远端接口抽象定义 RemoteApiGateway#sendBatch(List<RemoteMessage>) 接口；默认实现 MockRemoteApiGateway 用于演示/测试，生产可将 Feign/HTTP 实现替换。
5批量组装按 ID 升序（FIFO）一次抢占至多 batchSize 条 PENDING 消息，一次 sendBatch 即一次远端调用。
6并发控制线程池 remoteCallExecutor 核心/最大线程数 = concurrency，从线程池维度限制并发批次数。
7事务一致性enqueue 采用默认 REQUIRED 传播，加入主业务事务；消息写入与业务写入同生共死。
8抢占防重transitionStatus 用条件 UPDATE（WHERE status=:from）实现 CAS，避免并发调度重复发送。
9手动重试退避重试为「重置 FAILED → PENDING + 立即 dispatch」，由用户主动触发；retryCount 仅作追踪，不设自动最大次数。

二、偏差（Deviations）

  • 偏差需求中的「@transactionListener 注解」项目中并无同名自定义注解，实现为 Spring 原生 @TransactionalEventListener（语义等价，且项目笔记已记载该机制）。
  • 偏差需求中的「业务数据列表页面」后端项目无前端页面，落地为 REST 接口 GET /api/remote-messages（查询）与 POST /api/remote-messages/{id}/retry、POST /api/remote-messages/retry-failed（手动重试）。
  • 偏差未实现「定时自动重试」：需求第 3 点仅要求「手动重试」，故未引入 @Scheduled 定时任务（避免测试抖动）；自动退避作为后续扩展项。
  • 偏差「文件导入」场景通过新增 UserService#importUser 与 save 区分 bizType（IMPORT 与 CREATE），因此在 UserExcelImportListener 中由 save 改为 importUser。

三、权衡（Trade-offs）

备选方案弃用理由
业务方法内直接同步调用远端接口阻塞主流程、远端不可用时回滚业务，违背解耦与最终一致性目标。
MQ 消息队列（项目已有 RabbitMQ/RocketMQ）引入 Broker 的可用性/一致性复杂度；需求明确要求「本地消息表」，故采用 Outbox 模式，MQ 可作为后续投递通道。
「抢占 + 发送」合并为单个长事务远端调用期间长时间持有数据库事务，占用连接与行锁；拆分为短事务抢占 + 事务外发送。
Feign 真实远端服务演示项目无固定远端地址，且测试需确定性；以 RemoteApiGateway 抽象隔离，Mock 实现可一键替换。
为每条消息独立发起远端调用调用次数多、吞吐低；按批次组装请求参数统一发起，满足需求第 2 点。

四、未决问题（Open Questions）

  • 待确认远端接口的真实协议与鉴权方式（当前为 Mock；接入真实服务时需明确 URL、签名/Token、超时与幂等键）。
  • 待确认是否需要「最大自动重试次数 + 指数退避」的定时兜底发送（当前仅手动重试）。
  • 待确认消息清理策略：SUCCESS 历史消息是否需要归档/定期删除，避免消息表无限增长。
  • 待确认「文件导入」按行入队（一行一条 IMPORT 消息）是否与期望一致，或需改为「一次导入一批消息」。
