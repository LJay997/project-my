实现说明：远端接口调用本地消息表（Transactional Outbox）

针对「文件导入、数据新建、编辑、删除」四类业务场景接入远端接口调用，采用事务发件箱（Transactional Outbox）+ 本地消息表方案，实现异步解耦、批量发送、失败重试与状态全链路追踪。

一、设计决策（Design Decisions）

#决策点选择与理由
1事务监听机制使用 Spring 原生 @TransactionalEventListener(phase = AFTER_COMMIT)（即项目笔记中的「事务监听机制」），配合 @Async 在专用线程池异步执行。
2本地消息表新建 JPA 实体 RemoteMessage（表 t_remote_message），持久化远端请求参数（序列化为 JSON 字符串）。
3状态模型四态：PENDING / SENDING / SUCCESS / FAILED，配合 RemoteMessageLog 记录每次状态变更，形成全链路轨迹。
4远端接口抽象定义 RemoteApiGateway#sendBatch(List<RemoteMessage>) 接口；默认实现 MockRemoteApiGateway 用于演示/测试，生产可将 Feign/HTTP 实现替换。
5批量组装按 ID 升序（FIFO）一次抢占至多 batchSize 条 PENDING 消息，一次 sendBatch 即一次远端调用。
6并发控制线程池 remoteCallExecutor 核心/最大线程数 = concurrency，从线程池维度限制并发批次数。
7事务一致性enqueue 采用默认 REQUIRED 传播，加入主业务事务；消息写入与业务写入同生共死。
8抢占防重transitionStatus 用条件 UPDATE（WHERE status=:from）实现 CAS，避免并发调度重复发送。
9手动重试退避重试为「重置 FAILED → PENDING + 立即 dispatch」，由用户主动触发；retryCount 仅作追踪，不设自动最大次数。

二、偏差（Deviations）

  • 偏差需求中的「@transactionListener 注解」项目中并无同名自定义注解，实现为 Spring 原生 @TransactionalEventListener（语义等价，且项目笔记已记载该机制）。
  • 偏差需求中的「业务数据列表页面」后端项目无前端页面，落地为 REST 接口 GET /api/remote-messages（查询）与 POST /api/remote-messages/{id}/retry、POST /api/remote-messages/retry-failed（手动重试）。
  • 偏差未实现「定时自动重试」：需求第 3 点仅要求「手动重试」，故未引入 @Scheduled 定时任务（避免测试抖动）；自动退避作为后续扩展项。
  • 偏差「文件导入」场景通过新增 UserService#importUser 与 save 区分 bizType（IMPORT 与 CREATE），因此在 UserExcelImportListener 中由 save 改为 importUser。

三、权衡（Trade-offs）

备选方案弃用理由
业务方法内直接同步调用远端接口阻塞主流程、远端不可用时回滚业务，违背解耦与最终一致性目标。
MQ 消息队列（项目已有 RabbitMQ/RocketMQ）引入 Broker 的可用性/一致性复杂度；需求明确要求「本地消息表」，故采用 Outbox 模式，MQ 可作为后续投递通道。
「抢占 + 发送」合并为单个长事务远端调用期间长时间持有数据库事务，占用连接与行锁；拆分为短事务抢占 + 事务外发送。
Feign 真实远端服务演示项目无固定远端地址，且测试需确定性；以 RemoteApiGateway 抽象隔离，Mock 实现可一键替换。
为每条消息独立发起远端调用调用次数多、吞吐低；按批次组装请求参数统一发起，满足需求第 2 点。

四、未决问题（Open Questions）

  • 待确认远端接口的真实协议与鉴权方式（当前为 Mock；接入真实服务时需明确 URL、签名/Token、超时与幂等键）。
  • 待确认是否需要「最大自动重试次数 + 指数退避」的定时兜底发送（当前仅手动重试）。
  • 待确认消息清理策略：SUCCESS 历史消息是否需要归档/定期删除，避免消息表无限增长。
  • 待确认「文件导入」按行入队（一行一条 IMPORT 消息）是否与期望一致，或需改为「一次导入一批消息」。

实现说明：MyBatis-Plus 集成

在 spring 模块（Spring Boot 2.7.18）中集成 MyBatis-Plus 3.5.7，提供基于 H2 内存库、离线可运行的完整 CRUD 演示，覆盖逻辑删除、乐观锁、自动填充、分页与条件构造器。

一、设计决策（Design Decisions）

#决策点选择与理由
1依赖与版本选用 com.baomidou:mybatis-plus-boot-starter:3.5.7：对应 Spring Boot 2.x（Boot 3 才用 boot3-starter），与既有 BOM（spring-boot-dependencies 2.7.18）对齐，避免引入 Boot 3 专有 starter。
2接入方式直接复用工程已有的 H2 内存库 jdbc:h2:mem:testdb（application.properties 已配置 DataSource），不新增外部数据源。
3与 JPA 共存MyBatis-Plus 与既有 JPA/Hibernate 共用同一 DataSource、各自独立 ORM；仅对 mp_product 表走 MyBatis-Plus，不触碰 JPA 实体。
4建表方式用 schema.sql 自动建表并设置 spring.jpa.defer-datasource-initialization: true，确保 SQL 脚本在 Hibernate create-drop 之后执行，避免表被误删、保证离线可测。
5演示特性选取实体同时覆盖雪花主键（ASSIGN_ID）、逻辑删除（@TableLogic）、乐观锁（@Version）、字段自动填充（MetaObjectHandler）两类以上，满足示例要求。
6包结构新增独立包 com.qq.ijay997.mp.* 收敛 MP 相关代码，与既有 entity/repository/service（JPA）命名空间隔离，避免混淆。
7Service 层Service 继承 IService<Product>、Impl 继承 ServiceImpl<ProductMapper, Product>，复用 MP 通用 CRUD，分页/条件查询用 lambdaQuery() 演示。

二、偏差（Deviations）

  • 偏差逻辑删除字段 deleted 的默认值按字段初始化（private Integer deleted = 0;）而非通过 MetaObjectHandler 填充：strictInsertFill 仅对标注 @TableField(fill=...) 的字段生效，deleted 未标 fill，故改为实体初始值以确保插入时显式写入 0。
  • 偏差演示表名用 mp_product（前缀 mp_），与既有 JPA 表 t_user/t_remote_message 命名风格不同，用于一眼区分 MyBatis-Plus 演示数据。

三、权衡（Trade-offs）

备选方案弃用理由
新增 MySQL/独立数据源演示需要外部依赖、无法离线运行测试；复用 H2 内存库最省、最稳定。
把 JPA 的 User 实体改为 MP 实体会破坏现有 JPA 仓储、脱敏与 Outbox 两套链路，向后兼容要求不允许。
用 XML Mapper 演示 CRUD示例体量更大；BaseMapper + lambdaQuery() 已能覆盖全部演示点，注释清晰即可。
不引入 defer-datasource-initialization存在 Hibernate create-drop 与 schema.sql 顺序不一致的隐患，显式延后更稳妥。

四、未决问题（Open Questions）

  • 待确认生产环境若切换为 MySQL/PostgreSQL，PaginationInnerInterceptor(DbType.H2) 需同步替换方言，且 schema.sql 需按目标库改写。
  • 待确认雪花主键（ASSIGN_ID）是否为期望的主键策略；若对主键连续性有要求，可改为 AUTO（数据库自增）。
  • 待确认是否需要将 MyBatis-Plus 纳入既有敏感字段脱敏链路（当前演示实体不含敏感字段，脱敏机制未受影响）。

实现说明：MyBatis-Plus 关联查询与 level 字段

在既有 com.qq.ijay997.mp 模块上新增商品分类实体 Category（表 mp_category），与 mp_product 通过外键 category_id 关联，并用自定义 SQL（@Select）实现商品-分类关联查询；同时给 Product 与 Category 均新增 level 字段。

一、设计决策（Design Decisions）

#决策点选择与理由
1关联目标实体新增「商品分类」Category（表 mp_category），业务语义清晰，category_id 作为 mp_product 的外键。
2关联方式MyBatis-Plus 不支持 JOIN，故在 CategoryMapper 中用 @Select 手写 LEFT JOIN，返回 ProductCategoryVO。
3结果映射SQL 列别名用下划线（product_id 等），复用全局 map-underscore-to-camel-case: true 自动映射到 VO 驼峰属性，无需手写 ResultMap。
4两个查询方向① 分类侧 selectProductsByCategoryName（按分类名查商品）；② 商品侧 selectProductDetail（按商品 ID 查详情带分类），满足双向关联查询。
5分页配合增加 selectProductsByCategoryNamePage(Page, name)，首个参数用 Page，由 PaginationInnerInterceptor 自动生成 count 与 limit，验证 JOIN 与分页共存。
6level 类型两实体均用 Integer：等级/层级是数值语义，便于 BETWEEN/ORDER BY，支持 null（未评级/未分层）且占用小。
7逻辑删除过滤自定义 SQL 不走 MP 逻辑删除自动拼装，故手写 SQL 中显式带 p.deleted = 0。

二、偏差（Deviations）

  • 偏差Category 未加 @TableLogic（未做逻辑删除）：分类作为外键被引用，物理删除/逻辑删除会引入更多一致性处理，演示聚焦关联查询，保持 Category 表最简。
  • 偏差两个方向查询均用 LEFT JOIN（即使分类侧查询语义上更像 INNER JOIN）：保证分类信息缺失时商品仍能返回、不丢失行，符合 VO 的可空字段语义。

三、权衡（Trade-offs）

备选方案弃用理由
XML Mapper + resultMap需额外 XML 文件与 resultMap 配置；@Select + 下划线自动映射更简洁，且本项目 mapper-locations 下尚无 XML。
用实体嵌套（@TableField(exist=false) Category 对象）做关联需多次查询或依赖 MP 不支持的联表，无法单条 SQL 返回 VO，性能与语义均不如手写 JOIN。
通过 Service 层两次查询拼装 VON+1 查询、代码冗长；手写单条 JOIN SQL 更清晰高效。
新建独立关联 Mapper（如 ProductCategoryMapper）关联查询少（3 个），放进 CategoryMapper 即可，避免文件碎片化；后续增多再独立。

四、未决问题（Open Questions）

  • 待确认商品挂多个分类或多级分类树的场景是否在计划内：当前是单 category_id 一对多，仅支持一层分类；若需多级分类需引入 parent_id 树结构或中间关联表。
  • 待确认关联删除策略：Category 被商品引用时是否允许删除，是否需要在删除分类时对商品做 category_id 置空或级联处理。
  • 待确认若后续关联 VO 需暴露敏感字段，将重新评估是否接入 @Sensitive 脱敏链路（当前 VO 无敏感字段，未接入）。

实现说明：MyBatis-Plus 演示种子数据

在 schema.sql 中追加 4 个分类、11 个商品的幂等种子数据，便于启动后直接 curl 演示关联查询与分页/条件过滤。

一、设计决策（Design Decisions）

#决策点选择与理由
1幂等写法选用 H2 原生 MERGE INTO ... KEY(id)：以主键为匹配键，存在则更新、不存在则插入，单条语句原子完成，避免「先查再插」的竞态；对比 INSERT ... WHERE NOT EXISTS 更简洁。
2固定主键分类 1~4、商品 101~111：与 MyBatis-Plus 雪花主键（19 位）不冲突，且便于外键引用与幂等匹配。
3未分类场景保留 1 条商品（category_id = NULL），用于验证左连接/未分类语义。
4种子命名避让名称刻意避开测试关键字「苹果 / 香蕉 / 苹果派」，避免污染 ProductServiceTest.testConditionQuery 的 like('苹果') 计数断言。

二、偏差（Deviations）

  • 偏差种子数据直接写进 schema.sql（而非独立 data.sql）：用户明确指定该位置；且 schema.sql 与建表同源，天然保证表先于数据存在。
  • 偏差种子数据与测试共用同一脚本：未为测试单独做清库/隔离，而是通过「固定主键 + MERGE 幂等 + 命名避让」让断言不冲突。

三、权衡（Trade-offs）

备选方案弃用理由
data.sql 单独放种子与用户指定位置冲突；且 H2 内存库下 schema.sql/data.sql 顺序与 defer-datasource-initialization 的耦合更多一层心智负担。
INSERT ... SELECT WHERE NOT EXISTS每行需写存在性判断，冗长；MERGE 原生 upsert 更简洁、意图更清晰。
测试类里单独准备种子并按需清理无法满足「应用启动即有演示数据」的目标；且引入测试与生产数据双份维护成本。

四、未决问题（Open Questions）

  • 待确认固定主键 1~111 是否与未来人工/脚本写入的数据冲突风险：目前雪花主键位数不同、风险低，但若改变主键策略（如 AUTO 自增）需要重新评估。
  • 待确认种子数据若需经常调整，是否应抽离为独立的版本化 SQL 或 Flyway/Liquibase 迁移（当前项目未引入迁移框架）。

追加种子数据后，mvn -pl spring test -Dtest='ProductServiceTest,ProductControllerTest,CategoryServiceTest' 仍 12/12 通过，无条数断言被污染、无需调整测试期望值。

实现说明：LevelInterceptor 编译修复与审查

com.qq.ijay997.mp.interceptor.LevelInterceptor 是用户手写的数据权限拦截器：从 UserLevelHolder（ThreadLocal）取当前用户 level 阈值，对标注 @Level 的 Mapper 查询追加 alias.level <= threshold 条件。本次仅修复编译错误与一处别名解析缺陷。

一、设计决策（Design Decisions / 对意图的假设）

#假设依据
1这是一个"等级/数据权限过滤"拦截器，不是通用 SQL 改写器阈值来自 UserLevelHolder，条件为 level <= threshold，注解名 @Level
2保留 InnerInterceptor 实现，不改为 @Intercepts/Plugin.wrap用户已按 MP 的 InnerInterceptor 实现；这样能与 MybatisPlusInterceptor 内的其它拦截器统一排序
3只修编译错误 + 最小缺陷，不扩展功能未处理嵌套子查询、写操作等，保持原意图

二、偏差（Deviations）

  • 偏差SelectBody 在 jsqlparser 4.9 已移除 → 方法参数类型改为 Select（抽象基类，PlainSelect/SetOperationList 均继承它）。这是随依赖版本修正类型，不是换实现。
  • 偏差BoundSql 没有 setSql(String) → 改用 MP 的 PluginUtils.mpBoundSql(boundSql).sql(newSql)（与分页拦截器同一改写机制）。
  • 偏差jsqlparser 4.9 的 Column 无 (String, String) 构造器 → 改为 new Column(new Table(alias), column)。
  • 偏差rewriteSql 抛出 SQLException 但未声明 → 补 throws SQLException（调用方 beforeQuery 已声明）。
  • 偏差@AliasFor 只被 Spring 的注解工具处理，JDK 的 method.getAnnotation() 不生效：@Level("p") 实际只设置 value，tableAlias() 仍是默认 "a"，会生成非法列 a.level。已在拦截器内加 resolveAlias() 兜底。

三、权衡（Trade-offs）

备选方案弃用理由
改 CategoryMapper 为 @Level(tableAlias="p")会把修复散落到调用方；放在拦截器内统一解析更集中，且让 @Level("p") 的短写法如作者预期工作。
改为 MyBatis @Intercepts + Plugin.wrap与既有 MybatisPlusInterceptor（乐观锁 + 分页）顺序协调更麻烦；MP 推荐用 InnerInterceptor。
拦截所有 SELECT（无注解也给全表加条件）过于激进，会误伤非业务表；维持"仅注解方法生效"。

四、未决问题（Open Questions）

  • 待确认嵌套子查询（WHERE ... IN (SELECT ...)、EXISTS、JOIN 子查询）未被递归改写，类注释宣称"子查询嵌套 WHERE"能力有所夸大；如业务需要，需扩展 processPlainSelect。
  • 待确认resolveMapperMethod 只按方法名匹配，Mapper 存在同名重载时可能取错方法；如需支持应按参数类型匹配。
  • 待确认ConcurrentHashMap.computeIfAbsent 不缓存 null，类加载失败时会每次重算（性能小问题，不影响正确性）。
  • 待确认拦截器已在 MybatisPlusConfig 注册（第 28 行、位于最前），但全项目没有任何地方调用 UserLevelHolder.set()，当前处于"休眠"状态；需明确接入点（鉴权后 set、请求结束 finally remove）。
  • 待确认只过滤 SELECT，UPDATE/DELETE 未施加数据权限；是否要求写操作也受 level 约束需产品确认。

五、验证

一、设计决策（Design Decisions）

#决策点选择与理由
1查询场景选「p.price > (SELECT AVG(...) WHERE p2.category_id = p.category_id)」关联子查询：既能体现关联含义，又能展示子查询。

实现说明：身份上下文归并 + LevelInterceptor 职责拆分（阶段 1）

本次为纯重构：新建 com.qq.ijay997.auth 身份包，把用户身份/登录上下文从 masking、config 迁出；将 UserLevelHolder 合并进 UserContextHolder，使全项目只保留一个身份 ThreadLocal；把 LevelInterceptor 的"条件建模 + SQL 改写"下沉到 LevelConditionProvider。不扩展子查询递归、不覆盖 UPDATE/DELETE、不新增 ${} 片段通道。

一、设计决策（Design Decisions）

#决策点选择与理由
1包边界划分auth 承载"身份与授权模型"：UserPrincipal（用户身份 + 等级阈值）、UserContextHolder（请求级身份上下文）、PermissionCodes（权限码与角色映射）、MockUserContextFilter（HTTP → 身份适配）。masking 只保留"怎么脱敏"：Sensitive、SensitiveType、MaskRules、SensitiveValues、SensitiveJsonSerializer。
2PermissionCodes 归属它定义"谁能看什么"的权限词表与角色映射，属于授权模型；@Sensitive 只是引用其中的权限码。因此迁入 auth，脱敏规则仍留在 masking。
3MockUserContextFilter 归属其唯一职责是把 HTTP 请求头转换成 UserPrincipal 并写入上下文，属于身份基础设施；且它不包含任何脱敏规则，故从 config 迁入 auth。
4ThreadLocal 合并level 作为 UserPrincipal 的字段，由唯一 ThreadLocal（UserContextHolder）承载；getLevel() 在无上下文时返回 null；setLevel() 通过不可变副本替换主体。删除 com.qq.ijay997.mp.UserLevelHolder，避免两个 ThreadLocal 清理时机不一致。
5休眠语义MockUserContextFilter 不设置 level；clear()/remove() 后 getLevel() 必为 null，拦截器直接 return，不追加任何条件，与重构前完全一致。
6Provider 职责边界LevelCondition 只做值对象与标识符白名单校验；LevelConditionProvider 只做"注解 → 条件对象 → AST 改写"；LevelInterceptor 只做"读注解、读上下文、委托、写回 BoundSql"。
7改写等价性Provider 逐行搬运原有 JSqlParser 改写逻辑（WHERE 为空 / OR 加括号 / 普通 AND），并用 LevelConditionProviderTest 锁定三组黄金字符串。

二、偏差（Deviations）

  • 偏差@Level.value() 的默认值由 "" 改为 "a"：它与 tableAlias() 通过 @AliasFor 互为镜像，Spring 要求两者默认值相同，否则注解合成时抛出 AnnotationConfigurationException。该问题在迁移中由测试暴露；修正后别名解析结果不变。
  • 偏差UserPrincipal#getLevel() 加了 @JsonIgnore：/api/demo/masking/me 直接序列化 UserPrincipal，若不加会多出 "level": null 字段。为保持既有响应契约不变而隐藏该属性。
  • 偏差LevelCondition 对别名/列名做白名单校验（非法标识符抛 IllegalArgumentException）。正常注解值行为不变；只有错误配置从"生成非法 SQL 后由数据库报错"提前为"构造条件时快速失败"。
  • 偏差修正 Level 的 Javadoc：原文称"UNION 的每个分支都会被单独追加权限条件"，与实际实现（非 PlainSelect 顶层不改写）不符，已改为如实描述局限。

三、权衡（Trade-offs）

备选方案弃用理由
保留 UserLevelHolder 与 UserContextHolder 两个 ThreadLocal两套清理点容易遗漏其一，导致线程池复用时权限/等级串号；合并为单一上下文可从根上消除。
level 放在 UserContextHolder 的第二个静态字段仍是同一个 ThreadLocal 实例的两个值，需额外维护成对写入；放进不可变 UserPrincipal 更符合"身份即上下文"的语义。
方案 B：Service 传服务端生成的 ${} 片段本次明确不做。它新增 SQL 文本注入通道，且 ${} 在 getBoundSql() 阶段已展开，拦截器无法补参；留待后续单独评审。
方案 C：全面改用 QueryWrapperMP 不支持 JOIN，现有 CategoryMapper 的 JOIN 与关联子查询无法表达；改动与测试破坏面最大。
@SelectProvider 生成整段 SQL与 B 收益重叠但迁移成本更高，仅在动态 SQL 大量出现时才值得。

四、未决问题（Open Questions）

  • 已知局限子查询不递归改写：@Level("p") 只作用于外层 PlainSelect，p2/p3 等子查询表仍可被权限穿透（见 SubqueryQueryTest 的断言）。
  • 已知局限不覆盖 UPDATE/DELETE：只有 beforeQuery 改写，写操作无数据权限约束。
  • 已知局限无编程式片段通道：未提供非 @Level 查询的 ${} 片段入口，此类查询需显式标注 @Level。
  • 待确认生产环境由谁调用 UserContextHolder.setLevel()：当前仅测试与演示手动设置，需在认证流程中接入并在请求 finally 中 clear()。

实现说明：X-Level 请求头（HTTP 模拟数据权限）

在 MockUserContextFilter 中解析 X-Level，写入 UserPrincipal#level，使 HTTP 请求也能驱动 LevelInterceptor；非法值一律降级为"未设置"，保证向后兼容与不返回 500。

一、设计决策（Design Decisions）

#决策点选择与理由
1解析位置放在身份适配层 MockUserContextFilter，与 X-User-Id / X-Role / X-Permissions 同一处解析，随后经 5 参构造写入 UserPrincipal，不新增第二个 ThreadLocal。
2非法值策略缺省、空白、非数字（含 4.5、溢出 int）、负数统一返回 null：拦截器保持休眠、请求返回 200。理由是数据权限阈值属于可选的调试维度，脏 header 不应让整个请求失败，优先向后兼容。
3与权限码解耦X-Level 只写入 level；X-Permissions 覆盖角色预置权限的逻辑完全不动，两者互不影响。
4生效范围只有标注 @Level 的 Mapper 查询会被改写；未标注的查询即使带 X-Level 也不受影响，这是既有实现边界，不在本次扩展。
5测试组织新增 LevelHeaderIntegrationTest，而不是并入 SubqueryQueryTest：后者验证拦截器本身（编程式 setLevel），新类验证"HTTP → Filter → 上下文 → 拦截器"的适配链路，职责分离。

二、偏差（Deviations）

  • 偏差非法值选择"静默降级为未设置"而非返回 400：400 需要额外的错误响应契约与调用方改造，且会让"忘带/写错调试头"的请求整体失败；当前策略对正常业务零影响。
  • 偏差X-Level 不暴露在 /api/demo/masking/me 响应中（UserPrincipal#getLevel() 带 @JsonIgnore），保持既有响应契约；如需回显需显式调整。
  • 偏差文档中的「112 被过滤」演示使用分页接口，而该 SQL 的 name 条件当前被注释，因此演示的是等级过滤而非分类范围筛选，已在指南中注明。

三、权衡（Trade-offs）

备选方案弃用理由
非法值返回 400会改变既有接口的成功语义，且与"仅用于调试的模拟头"定位不符；fail-safe 更符合最小惊讶原则。
在 Controller / @ControllerAdvice 解析 X-Level数据权限是横切关注点，放在 MVC 层会漏掉非 Controller 入口，也无法与请求清理生命周期绑定。
把 X-Level 并入 X-Permissions 之类字符串语义混杂、解析更复杂；独立 header 与 level 字段一一对应，便于调试与文档化。
不限制负数，直接作为阈值负数会让 level <= -1 过滤掉全部数据，容易被误用成"隐藏所有数据"；降级为未设置更安全。

四、未决问题（Open Questions）

  • 待确认生产环境是否允许客户端直接传 X-Level：当前仅用于本地 mock，真实环境必须由认证流程从服务端会话/Token 推导，不能信任请求头。
  • 待确认是否需要上限校验（例如 max=10）或白名单等级：现在任意非负整数都接受。
  • 已知局限仅 @Level 查询生效；未标注的查询带 X-Level 也不会被过滤。
  • 已知局限子查询穿透、UPDATE/DELETE 不覆盖，与阶段 1 记录一致。

实现说明：8082 运行期 42104 诊断与 H2 内存库生命周期修复

现象：GET /api/mp/categories/products/page?name=手机数码&current=1&size=20（X-Level: 3）返回 SQL 执行错误 SELECT COUNT(*) AS total FROM mp_product p WHERE p.deleted = 0 AND p.level <= 3 [42104-214]。 结论：42104 = TABLE_OR_VIEW_NOT_FOUND_DATABASE_EMPTY_1（"表不存在，且数据库为空"），不是列不存在（列不存在是 42122）； 根因是内存库在连接池连接被全部关闭后销毁，而 schema.sql 只在启动时执行一次，之后的请求落到空库上。 最小修复：给数据源 URL 增加 DB_CLOSE_DELAY=-1（仅一行配置，不改 schema、不改分页/别名逻辑）。

一、设计决策（Design Decisions）

#决策点选择与理由
1不改 schema.sqlCREATE TABLE IF NOT EXISTS mp_product 已直接包含 level 与 category_id，全文没有任何 ALTER TABLE ADD COLUMN，源文件与 target/classes 的 MD5 一致；因此"旧表缺列"不是本次现象的原因，无需改动。
2不改分页 count SQL / 拦截器报错语句的 p.deleted / p.level 别名与 PaginationInnerInterceptor 生成的 count 形态本身合法；42104 表示整库无表，与别名解析无关，所以不做任何 SQL 层改动。
3改数据源 URLjdbc:h2:mem:testdb → jdbc:h2:mem:testdb;DB_CLOSE_DELAY=-1：把内存库的存活期绑定到 JVM，而不是"最后一个连接"，从机制上消除空库。
4不恢复 name 过滤CategoryMapper#selectProductsByCategoryNamePage 中按分类名过滤的行仍保持注释状态（用户未批准），仅在本文件中记录现状。

二、偏差（Deviations）

  • 偏差问题落在配置层而非代码层，因此本轮只改一行配置，没有引入"启动后自检表结构"或"每次请求重建 schema"之类的新机制。
  • 偏差保留 spring.jpa.hibernate.ddl-auto=create-drop（JPA 表仍随上下文关闭而删除），只修 H2 库级生命周期，避免扩大改动面。

三、权衡（Trade-offs）

备选方案弃用理由
只重启 8082，不改配置重启能立刻恢复，但配置缺陷仍在：连接池连接被回收后库还会被销毁，数小时后再次 42104，属于可复现的定时炸弹。
每次请求前重建 schema 或开启 spring.sql.init.mode=alwaysSQL 初始化只在启动阶段运行一次，请求期重建需要自定义逻辑，成本高且会与 seed 数据、事务边界纠缠。
改用文件库 jdbc:h2:file:...会改变演示定位（离线/免落盘）并引入数据残留与清理问题，超出本次最小修复范围。
给表加 ALTER TABLE ADD COLUMN IF NOT EXISTS level本就不缺列；且对"整库为空"无效，属于误诊式修改。

四、未决问题（Open Questions）

  • 待确认是否需要在启动时增加"关键表/列存在性"自检，把 42104 提前暴露为启动失败（当前是首次请求才暴露）。
  • 待确认products/page 的 name 过滤是否恢复：现状是分页查询忽略分类名条件，仅按 deleted 与等级过滤。
  • 运维修改配置后必须重启 JVM（H2 内存库与 schema 只在新进程中重建）；仅热替换 class 不会让 URL 生效。
